# Runtime database privilege separation (review only)

The existing runtime executes administrative/post schema preparation during startup. To preserve deployment compatibility, the default remains legacy-prepare until a supervised migration/role review. The new PROFINO_RUNTIME_SCHEMA_MODE=verify-only path performs only catalog inspection inside a bounded read-only transaction; on missing objects or access mismatch it stops startup, never falls back to DDL.

This is a narrow compatibility inventory for existing operational tables and the post-history trigger. It is not a complete least-privilege, trigger-body, type, sequence, column-level permission, row-level security or financial schema audit. The restricted runtime role must separately pass database-access, catalog, actual registration/admin/post behavior and backup restore checks. A missing or incompatible object is a release blocker, not permission to elevate the bot role or apply production changes. No role, setting, migration or deployment has been changed. Keep the current private network and financial operations disabled.

In verify-only mode the inventory additionally checks ledger read access and account creation required by registration. It rejects direct table/column writes on ledger journals and entries, updates to ledger accounts or audit/history records, ownership, destructive privileges, schema/database CREATE and privileged role membership. This is a conservative pre-financial role contract (table-wide grants for needed operational operations); it does not establish safety of arbitrary security-definer functions, other schemas, indirect privileges, RLS, sequence grants, trigger bodies, or a future separately authorized posting role. Do not switch production modes until its real role and schema have been inspected and the restricted startup rehearsed.

### Restricted owner membership locking
PostgreSQL SELECT FOR SHARE requires UPDATE privilege on at least one column of each locked table. The legacy direct lock is therefore incompatible with forbidding admin_users writes. The review-only migration migrations/20261124_restricted_owner_lock.review.sql defines a fixed, no-argument SQL security-definer function that returns only the configured active owner's internal ID and holds the membership/user locks within the caller transaction. No writes or dynamic SQL. The restricted startup verifier requires the exact body, return type, language, volatility, security-definer flag, fixed search path, non-runtime ownership, runtime EXECUTE and no PUBLIC EXECUTE. Restricted admin audit/status paths use it; legacy mode remains unchanged. Before any production execution, review the actual tables and function owner (dedicated minimally privileged trusted role, not runtime), grant EXECUTE narrowly, check all function/role grants and rehearse actual concurrent revocation, registration, sequence grants and admin workflows. The disposable fixture proves the lock permission boundary, not actual production role or deployment readiness.

### Column and generated-ID contract
The verify-only policy now requires explicit column write privileges matching current runtime SQL, including rejecting excess grants on unlisted columns, identity columns, and immutable ledger/audit data. It verifies owned serial/identity generator metadata for five existing insert paths, serial USAGE, and rejects sequence UPDATE/ownership or delegable USAGE. Identity generation does not require direct sequence USAGE. Custom ID generators or unmatched live schemas require review, not broad grants. A disposable PostgreSQL fixture exercises actual grammY registration, repeat registration and wallet view under these narrow grants. This is a deliberately conservative contract, not a production permission migration; actual grants, security-definer owners, RLS, other tables/schemas and complete administrative workflows remain subject to operational review.

### One-shot operator evidence
After a separately authorized code deployment (not before), the same runtime DSN may be inspected using `node scripts/audit-restricted-runtime.js` via the existing authorized private runtime, with no credentials in command arguments or logs. This emits only a fixed JSON status and bounded reason enum, never writes, creates roles or starts Telegram. Exit 0 means the narrow inventory/privilege contract passed, 2 means a known incompatibility, 3 means unavailable/cleanup failure. It always reports financialActivationReady=false. Run once, not as a recurring schedule. This does not grant access or authorize changes. Production execution and real role evidence remain outstanding.

### Behavioral admin and history replay
The post-history trigger now shares its exact reviewed legacy function body between startup preparation and catalog inspection. Verify-only rejects a no-op or altered body, unexpected language, security-definer mode, runtime function ownership or other incompatible function metadata. The isolated PostgreSQL fixture runs actual restricted admin status posting (including revoked membership and replay), activity audit, and post-history insert/update. Only the fixed public owner-lock function identifier is redirected by the fixture to its random test schema. No live role or data is used; this does not verify other production triggers or authorize schema preparation.

Verify-only also rejects a changed current role relative to session authorization, any membership in another role (including non-inherited membership), and delegable EXECUTE on the fixed owner-lock function. The fixture models the restricted session with SET SESSION AUTHORIZATION and checks rejection of SET ROLE and non-inherited membership. The real production login, provider-specific roles and all other role grants remain unverified; the fixture starts from a disposable privileged connection and does not prove the live login configuration.

### Read-only diagnostic transaction evidence
The shared diagnostic wrapper requires explicit BEGIN, SET and COMMIT acknowledgements and inspects effective read-only, repeatable-read, statement and lock timeout settings before any catalog work. The FadeHost one-shot audit uses that same wrapper and retains its existing output contract. Unknown or incompatible settings fail closed; no production diagnostic was executed. PostgreSQL fixture verifies actual session settings and DDL rejection in the disposable database. This proves the reviewed diagnostic boundary only, not production permissions or financial readiness.

### Pre-financial application object boundary
Verify-only rejects direct write/destructive privileges or ownership on additional persistent relations in the inspected application schema, including unlisted tables, views, materialized views and foreign tables. Callable unreviewed SECURITY DEFINER functions/procedures in that schema also block startup; the one explicitly verified owner-lock function is the sole exception. Disposable tests exercise column-level deposit privileges, withdrawal deletion, future financial tables/views and default PUBLIC EXECUTE on a synthetic privileged function. This is intentionally a conservative restriction for the existing non-financial runtime, not a grant migration or proof of all indirect paths: other schemas, trigger chains, ordinary functions, rules, row policies and the real provider role still require independent review. No production changes.

### Expanded current-connection privilege evidence
The existing manual database-access audit now reports session/current role equality, origin replication mode, permission to SET session_replication_role, effective ledger INSERT/UPDATE (including column-only grants), DELETE, delegable write privileges, PUBLIC table/column write grants and RLS-enabled table counts. These are bounded flags and counts, not a least-privilege verdict; an audit role is not necessarily the deployed runtime role. Disposable PostgreSQL regression exercises a non-login role, explicit column grants, PUBLIC grants, grant option, DELETE, RLS and parameter permission, then removes all fixture objects. No production grants, role settings or data are changed. The live runtime DSN, role membership paths, actual RLS policies and other schemas still need separately authorized evidence.

The manual role diagnostic now separately reports whether the session login can SET ROLE to another role or a reviewed ledger function/table owner, whether reviewed ledger functions have PUBLIC EXECUTE (including PostgreSQL's default grant), and whether the current role can execute any SECURITY DEFINER routine in the inspected schema. It does not disclose names or execute the routines. The disposable test models session authorization and non-inherited role membership, grants and revokes EXECUTE, and removes fixture objects. These are findings, not an automatic least-privilege decision: the reviewed owner-lock routine may legitimately be callable, and other schemas, actual function resolution, RLS semantics and the real production login remain unverified.

The database-access audit now distinguishes enabled, forced-and-enabled and current-role-effective row-level security, and counts ledger tables carrying any policy or a permissive PUBLIC write policy (including policies on currently disabled tables). It emits no policy names or expressions. PUBLIC policy applicability is not equivalent to an actual SQL grant; a restrictive predicate may be legitimate. The disposable regression contrasts superuser bypass with a restricted role, tests policy removal/disabled RLS and rejects inconsistent count evidence. These findings are not a policy semantics audit or release approval; function resolution, actual production login and operational security remain unverified. No production schema or grants changed.

### Restricted runtime resolution and trigger enforcement
Verify-only startup now requires an effective resolution path containing exactly pg_catalog first and the reviewed application schema second, origin replication mode, and absence of permission to SET session_replication_role. This closes a gap between the existing diagnostic and the pre-financial startup guard. The disposable fixture rejects reordered/extra visible schemas, a parameter SET grant, and non-origin mode, and rechecks the restored baseline. The historical legacy-prepare mode is unchanged. Effective path verification is a single checked-out session snapshot; it does not prove every pool connection, absence of future temporary objects, function resolution for a different posting role or actual production configuration. No live settings or privileges are changed; a mismatched legitimate environment requires review, not automatic elevation.

Restricted pool creation now shares a fixed startup path with the one-shot diagnostic: pg_catalog, public, then pg_temp explicitly last. This applies on each newly created connection and prevents implicit temporary-schema precedence over the reviewed tables; connection URL options are rejected in restricted mode rather than merged. Legacy mode is unchanged. The disposable two-connection regression checks independent backends and temporary-table name collision resolution. This does not prevent a later explicit session SET, establish the deployed role, or certify a future posting pool. No live configuration or grants changed.

In verify-only runtime mode the pool now checks effective search path, session/current role equality and origin replication mode on each checkout, for promise clients and pool.query callback consumers. A mismatched or failed probe discards the client and returns a fixed error before application SQL is dispatched. The disposable test changes a reused session's search path and replication mode, verifies rejection and fresh connection recovery. This is not a transaction-idle guarantee or protection from changes made after checkout, and adds one database round trip per checkout. Legacy mode remains unchanged; real pool configuration and performance are unverified. No production deployment, role or data changes.

Restricted connection checkout and release now require the documented pg Client.getTransactionStatus API. An active, aborted or unknown transaction is never handed to application SQL; a new connection may initially report null but its completed probe must report idle. Release destroys a non-idle connection instead of committing or silently reusing it. The declared pg minimum matches the already locked 8.23.1 version; no installed dependency version changed. Disposable tests verify rollback on disconnect for unfinished/aborted writes and normal committed connection reuse. This does not cover concurrent misuse of a checked-out client or later in-session privilege changes. Legacy mode remains unchanged; production deployment and operational verification are outstanding.

### Reviewed runtime row visibility checkpoint
Verify-only now requires each of the nine reviewed operational/ledger relations to be a permanent ordinary table with no enabled or forced row-security flag or dormant policy. A restricted role can hold the expected grants yet see filtered data; grants alone are insufficient. This is a conservative historical contract for the existing non-financial runtime, not a general finding against RLS or partitioning. Disposable tests reject enabled RLS on admin membership, a dormant force flag on ledger entries and a dormant policy on users, restore the baseline, and continue real offline registration and admin tests. The operator CLI emits RELATION_POLICY_INCOMPATIBLE without object names. Legacy startup is unchanged. Actual runtime catalog, policy semantics, function owner, backup and live readiness remain unverified. No production DDL or financial authorization; exact-head CI required.

### Reviewed runtime relation topology checkpoint
The same restricted startup inventory now requires no inheritance links in either direction and no rewrite rules on its nine required relations. Ordinary permanent relkind alone cannot exclude inherited child rows or SQL rules that suppress/redirect a runtime write. The disposable test adds a child relation, a parent relation and an INSERT suppression rule, requires the fixed sanitized incompatibility error, then removes each fixture before the existing offline bot tests. This is a conservative contract for the reviewed non-financial runtime; legitimate alternative topology needs separate review. Legacy mode and actual production schema are unchanged. Exact new-head CI, live catalog, privileges and release approval remain required.

### Scheduled-post trigger inventory (2026-11-26)
The reviewed `scheduled_posts` contract permits exactly one noninternal trigger, the named history trigger with its existing reviewed definition and metadata. Additional user triggers, even disabled, invalidate the verify-only inventory; internal foreign-key triggers are not included in this specific check. Disposable PostgreSQL tests cover an added BEFORE UPDATE trigger that suppresses changes, its disabled state, and restoration of the reviewed inventory. ### Operational generated-ID policy (2026-11-26)
The five verified serial/identity generators must also be permanent, noncycling, increment by one, and have a positive minimum and start at or above that minimum. This complements the existing ownership, default and permission checks. The disposable restricted-role fixture exercises serial CYCLE, identity increment drift and a zero minimum, then restores the reviewed configuration. This intentionally does not attest current sequence positions, exhaustion headroom, or the complete live ID type/constraint contract. Different live generator policies require explicit review, not automatic ALTER SEQUENCE. No production DDL or grants changed. Exact-head CI required.

### Unreviewed sequence access (2026-11-26)
The restricted inventory now identifies the exact five reviewed sequence OIDs and rejects effective USAGE, UPDATE or ownership on every other sequence in the application schema. USAGE permits nextval and UPDATE permits setval independently of table grants. Disposable tests cover direct USAGE/UPDATE and inherited PUBLIC USAGE, followed by restoration. Read-only sequence SELECT is not prohibited by this specific rule; other schemas, actual grants and live sequence positions remain separate release gates. No production permissions or sequence values changed. Exact-head CI required.

### Restricted session comparison integrity (2026-11-26)
Checkout and inventory session identity, effective schema order and replication-mode equality now explicitly use pg_catalog operators and catalog text types. A disposable PostgreSQL fixture installs a schema-local text-array equality that falsely reports a drifted path as correct using ordinary equality; the pinned comparison must reject the session and discard the connection. This is narrowly scoped to these session comparisons, not certification of every SQL operator or arbitrary untrusted schema. No production grants, DDL or runtime configuration changed. Exact-head CI required.
